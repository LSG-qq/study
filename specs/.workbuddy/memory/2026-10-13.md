## 评审《Java 全栈地基计划（一年）》

文件：`D:/qmm/docs/specs/2026-10-13-Java全栈地基计划-design.md`

结论：方向可行，排期不可行。共 5 条问题（2 阻断 / 2 建议 / 1 提示）。

量化结论（评审中推算，非原文数据）：
- 名义可用 20h/周 × 52 周 = 1040h；计划需求（四阶段 910h + 嵌入模块 ~37h）≈ 947h
- 按 70% 执行率折算实际投入 728h，缺口 ≈ 220h
- 60/30/10 比例下编码预算 ≈ 300h，而实践任务真实编码需求估 310–435h（中值 370h）
- 前 17 周无任何可运行后端产出；第 18 周才出现第一个真实 REST API

主要风险：
1. 时间账乐观（阻断）—— 20h/周被当成常量；实践编码未计入预算表
2. 前 17 周动机真空（阻断）—— 与"在职边做边学 + 手上已有 RuoYi 真实项目"的现实脱节
3. 无中途熔断（建议）—— 全年仅 5 个验收卡点，平均 9 周一个
4. 无砍单优先级清单（建议）
5. P3 标称 7 周但正文周号只排到第 28–32 周（5 周）；:26 写"剩余 ~2 周机动"，实际 8–10 周

建议三刀：
- 换靶子：用 RuoYi-Vue 工单系统（Spring Boot + MyBatis + Redis + MySQL + Nginx，正好命中 P2/P3）替代虚拟的 uni-app 商城
- 改比例：60/30/10 → 40/45/15
- 加熔断：每月自检，落后 ≥2 周即启动砍单

砍单优先级（从上往下）：Vue3 源码 36–65 集 → CSS 查漏 → 计网（转字典）→ P4 可选进阶 → MyBatis-Plus 代码生成器。
绝不砍：断点调试、工程化、MySQL 索引与事务、Spring Boot 接口分层、部署贯通。
